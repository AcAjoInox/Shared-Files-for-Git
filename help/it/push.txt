GIT-SHARED-PUSH(1)

NOME
    git shared push - invia al creatore le versioni pubblicate

SINTASSI
    git shared push [<remote>] [--] [<path>]

DESCRIZIONE
    Per un file condiviso attraverso un remoto (beta), invia al suo
    creatore, il repository remoto dove stanno le versioni ufficiali, le
    versioni gia' pubblicate qui. Si invia solo la catena delle versioni,
    mai il progetto. Come 'git push' dopo 'git commit': publish crea la
    versione, push la invia. publish, update e status non usano mai la
    rete; push, pull e 'status --remote' si'.

    La prima volta, 'git shared push <remote> <path>' rende <remote> il
    creatore del file: una versione nuova, con lo stesso contenuto
    dell'ultima, ne registra l'URL e viene inviata li'. I peer locali la
    ricevono come ogni altra versione.

    Da quel momento push invia l'ultima versione al creatore, e una copia
    a <remote> (default: origin), per chi clona questo repository. Il
    creatore accetta solo una versione che segue la sua, e solo da chi
    puo' scrivere li'. Se ha una versione piu' nuova, lancia
    'git shared pull', committa e lancia di nuovo push. Se non puoi
    scrivere li', la versione resta qui (e nel tuo remote) come proposta.

    Se il file ha un sovrano (git shared crown), push invia al sovrano:
    e' lui l'autorita' del file. Il creatore non cambia mai.

    Se l'autorita' ha meno di due eredi, il tuo remote diventa uno di
    loro (git shared crown --help, EREDI): push invia una versione che
    lo registra, e la tiene qui solo se l'autorita' la accetta. Senza
    permessi di scrittura non cambia nulla. git config shared.heir
    false tiene fuori il tuo remote. Se l'autorita' non risponde e il
    tuo remote e' un erede, push dice come prenderne il posto.

    Senza <path>, tutti i file che hanno un creatore, con un push per
    creatore; i file senza creatore si saltano. Il primo argomento e' un
    <remote> se questo repository ha un remote con quel nome; dopo '--'
    e' sempre un path.

    push non chiede mai la password: usa le credenziali che git ha gia'
    (credential helper, chiavi ssh). Se mancano, la versione non e'
    accettata; un normale 'git fetch' o 'git push' verso quel remote le
    imposta. Un remote dato come path relativo si scrive nella catena
    come path assoluto. Lo stesso remote scritto in un'altra forma
    (https:// o git@, con o senza .git) vale come lo stesso.

    Nella catena va l'URL del remote come e' configurato
    (remote.<name>.url), non come lo riscrive url.<base>.insteadOf
    sulla tua macchina: i lettori vedono https://... anche se tu fai
    push via ssh. Le credenziali nell'URL (un token, utente:password)
    non si scrivono mai e non si stampano: push avvisa e le toglie. Per
    raggiungere un URL che e' uno dei tuoi remote, push e pull passano
    da quel remote, come 'git push <remote>': valgono il suo pushurl,
    le regole insteadOf e le credenziali.

ESEMPI
    git shared push origin common.h   # origin diventa il creatore
    git commit -am "Corretto il timeout in common.h"
    git shared publish
    git shared push

VEDI ANCHE
    git shared pull --help, git shared publish --help,
    git shared status --help, git shared crown --help
