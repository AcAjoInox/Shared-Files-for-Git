GIT-SHARED-LINK(1)

NAME
    git shared link - link a file shared by another repository

SYNOPSIS
    git shared link [-c | -m <message>] [-f | --merge] [--adopt]
                    [--] <source-file> [<destination>]
    git shared link [-c | -m <message>] [-f | --merge] [--adopt]
                    [--] <url> <id> [<destination>]

DESCRIPTION
    Links to this repository a file that another repository shares.
    <source-file> is the path of the file in the other repository, as
    you see it on disk. The file is written from its latest version and
    staged with .gitshared.

    When they are committed the repositories become peers: each one
    learns about the other and about the other peers. To cancel before
    the commit:
        git restore --staged --worktree .gitshared <destination>
    (only .gitshared, if the destination already existed).

    The destination path is the same as in the source, unless
    <destination> is given.

    If the destination already exists (for example a copy made by hand)
    the file is kept as it is, and only .gitshared is staged. After the
    commit 'git shared status' tells how it compares with the shared
    version: aligned, new version to apply, or diverged (update merges
    it). It must be tracked by git, and it must have something in
    common with the shared file: its content, or a past content, is one
    of the shared versions. If not, link stops: --merge links it anyway
    and 'git shared update' merges the two files, with conflicts where
    they differ; -f overwrites it with the latest version.

    If the destination is already shared with another ID (for example
    'git shared set' was run in both repositories), link stops: --adopt
    takes the ID of the source. The same commit unlinks the old ID, as
    'git shared unlink' does, and links the new one.

    After a clone, the file is declared in .gitshared but not linked
    (status says "unlinked"): link it again from one of its peers. The
    file is not touched, and the link works at once, without a commit.

REMOTE (PROTOTYPE)
    With <url> <id> you link a file published to a remote (see
    'git shared publish --help'): <url> is its creator, or a repository
    that has a copy; <id> is the ID of the file, which 'git shared status'
    shows in every repository that uses it. Only the version chain is
    fetched, not the project. The default destination is the name of
    the file.

    This repository becomes nobody's peer and the creator records
    nothing: new versions come from the creator, which 'git shared
    status', 'publish' and 'update' ask every time.

    After cloning a repository that uses a remote file, link it again
    from the URL of the clone: the chain there tells who the creator is.

OPTIONS
    -c, --commit
        Commit .gitshared and the file right away. Nothing else staged
        goes into the commit.

    -m <message>
        Like -c, with <message>.

    -f, --force
        Overwrite an existing destination with the latest version.

    --merge
        Link an existing destination that has nothing in common with
        the shared file. After the commit it is diverged: 'git shared
        update' merges them.

    --adopt
        The destination is already shared with another ID: take the ID
        of the source.

EXAMPLES
    git shared link -c ../firmware-a/include/common.h
    git shared link -c ../firmware-a/include/common.h inc/common.h
    git shared link --adopt -c ../firmware-a/include/common.h
    git shared link -c https://github.com/luca/A \
                    0f8c3e5a9b2d4c71a6e0d9b8c7f61234 inc/common.h
