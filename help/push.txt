GIT-SHARED-PUSH(1)

NAME
    git shared push - send the published versions to the creator

SYNOPSIS
    git shared push [<remote>] [--] [<path>]

DESCRIPTION
    For a file shared through a remote (beta), sends the versions
    already published here to its creator, the remote repository where
    the official versions are. Only the version chain is pushed, never
    the project. Like 'git push' after 'git commit': publish creates the
    version, push sends it. publish, update and status never use the
    network; push, pull and 'status --remote' do.

    The first time, 'git shared push <remote> <path>' makes <remote> the
    creator of the file: a new version, with the same content as the
    latest one, records its URL and is pushed there. The local peers
    receive it as any other version.

    From then on push sends the latest version to the creator, and a
    copy to <remote> (default: origin), for whoever clones this
    repository. The creator takes only a version that follows its own,
    and only from who can write there. If it has a newer version, run
    'git shared pull', commit and push again. If you cannot write there,
    the version stays here (and in your remote) as a proposal.

    If the file has a sovereign (git shared crown), push sends to the
    sovereign instead: it is the authority of the file. The creator
    never changes.

    If the authority has fewer than two heirs, your remote becomes one
    (git shared crown --help, HEIRS): push sends a version that records
    it, and keeps it here only if the authority takes it. Without write
    access nothing changes. git config shared.heir false keeps your
    remote out. If the authority does not answer and your remote is an
    heir, push says how to take over.

    Without <path>, all the files that have a creator, with one push for
    each creator; files without a creator are skipped. The first
    argument is a <remote> when this repository has a remote with that
    name; after '--' it is always a path.

    push never asks for a password: it uses the credentials git already
    has (credential helper, ssh keys). If they are missing, the version
    is not accepted; a plain 'git fetch' or 'git push' to that remote
    sets them up. A remote given as a relative path is recorded in the
    chain as an absolute one. The same remote written in another form
    (https:// or git@, with or without .git) counts as the same.

    The chain records the URL of the remote as it is configured
    (remote.<name>.url), not as url.<base>.insteadOf rewrites it on
    your machine: readers see https://... even if you push over ssh.
    Credentials in the URL (a token, user:password) are never recorded
    nor shown: push warns and leaves them out. To reach a URL that is
    one of your remotes, push and pull go through that remote, as 'git
    push <remote>' does: its pushurl, insteadOf rules and credentials
    apply.

EXAMPLES
    git shared push origin common.h   # origin becomes the creator
    git commit -am "Fix the timeout in common.h"
    git shared publish
    git shared push

SEE ALSO
    git shared pull --help, git shared publish --help,
    git shared status --help, git shared crown --help
