GIT-SHARED-UPDATE(1)

NAME
    git shared update - get the new versions and apply them

SYNOPSIS
    git shared update [-f] [--scan] [-c | -m <message>] [<repo>] [<path>]
    git shared update --peers [--scan] [-m <message>] [<path>]
    git shared update (--ours | --theirs) [-c | -m <message>] [<repo>]
                      [<path>]
    git shared update --abort [<repo>] [<path>]

DESCRIPTION
    Receives the versions the peers announced and writes the latest one
    into the file and the index. Nothing is committed unless -c or -m is
    given. Only the peers that announced something are fetched from.
    A repository that announced a version but is not a peer of this one
    is not fetched from: update says to run 'git shared update --peers'
    in that repository. Joining the peers stays your choice.

    Changes that are not committed, even staged ones, are never
    overwritten: update stops, unless -f is given. A version applied by
    an earlier update and not committed yet is not a change of yours.

    Merging. If you changed the file on an older version, or two peers
    published without seeing each other, update merges the versions as
    git merge does. After a clean merge the file is "applied, to
    commit": commit it, then 'git shared publish'.

    On a conflict the file gets the usual markers and git status shows
    it as unmerged. Fix the file, then:
        git add <file>
        git shared update -c
        git shared publish
    Or keep one of the two versions, whole, instead of fixing the file:
        git shared update --ours -c      (yours)
        git shared update --theirs -c    (the other one)

    Binary files are never merged, even when the changes do not touch
    the same bytes: it is always a conflict. The file keeps your version,
    with no markers, and the other one is in the index:
        git show ':3:<file>' > other-version
    Then choose with --ours or --theirs.

    To give up the merge:
        git shared update --abort
    The file goes back to the last commit and the merge is dropped, in
    one step. A plain 'git restore -s HEAD -SW -- <file>' works too, but
    only from the next git shared command on: a change staged before
    that would be taken as the resolution.

    Without <path>, all the shared files; with it, only that one.

    Another repository. If the first argument is a folder, update works
    on that repository, without moving there; <path> is then relative to
    that folder. A shared file is never a folder, so there is no doubt:
        git shared update ../app             (every shared file of app)
        git shared update ../app inc/conf.h  (only that one)
    It is the same as 'git -C ../app shared update [<path>]'.

    Every peer at once. With --peers, update brings this repository and
    every local peer of its shared files (only the peers of <path>, if
    given) to the latest version, and commits in each one: you do not
    need to visit the other repositories. The peers work in parallel, so
    it takes about as long as the slowest one. In a peer, update only
    does what is safe without someone looking at it: it applies a new
    version to a file with no local changes. It skips, and says why:
        - a file with local changes, diverged, or with versions to merge;
        - a file suspended on the branch the peer is on;
        - a peer in the middle of a git merge, rebase, cherry-pick or
          revert, or with a detached HEAD;
        - a peer that opted out with 'git config shared.peerUpdate false'.
    Each line of a peer starts with its path. The exit code is 1 if a
    peer was left with something to do by hand.

    A file committed here but not published: the peers get the last
    published version, not your change. Run 'git shared publish' first.

OPTIONS
    -f, --force
        Overwrite changes that are not committed.

    --peers
        Also update and commit every local peer, in parallel (see
        above). Not with -f, --abort, --ours, --theirs or <repo>; -m
        sets the message of every commit.

    --scan
        Fetch from every peer, not only from the ones that announced a
        new version: for a notice that got lost, for example while this
        repository was moved or could not be reached.

    -c, --commit
        Commit the applied or merged files right away. Nothing else
        staged goes into the commit.

    -m <message>
        Like -c, with <message>.

    --ours, --theirs
        Finish the merge in progress keeping your version (--ours) or
        taking the other one (--theirs), whole: for a binary file, or
        for a text file instead of fixing the markers. The chosen
        version goes into the file and the index, then update goes on
        as usual; keeping yours is a choice, not a way to give up.
        Without <path>, every shared file with a merge in progress. If
        the resolution is already staged (git add), finish it with
        'git shared update' or give up with --abort.

    --abort
        Give up the merge in progress: the file goes back to the last
        commit, in the index and in the working tree. Nothing is fetched
        and the latest version does not change. Without <path>, every
        shared file with a merge in progress.

NOTES
    Line endings: every repository must normalize the file the same
    way. If the source commits it with CRLF and this repository has the
    'text' or 'eol' attribute for it, the version just applied looks
    modified, and committing it makes a new version that changes every
    line. Give the file the same attribute everywhere, for example the
    line '<path> text' in .gitattributes.

    The executable bit is not shared: the file is always written with
    mode 100644.
